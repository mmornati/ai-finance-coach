# Borrow the plumbing, build the coach

The project is feasible, legal for personal use, and cheap to run. Most of it already exists. Bank sync through Enable Banking, LLM categorization, a local UI and chat over transactions are all covered by open-source tools: Actual Budget, Firefly III, actual-ai, Sure and the small Syllogic project. **No project combines a persistent memory of off-bank liabilities, contract review, a search for cheaper alternatives tied to detected subscriptions, and proactive coaching for EU users.** That gap is the reason to build. Demand exists. OpenAI launched a Plaid-backed personal-finance product in May 2026, and Anthropic is testing a "Money" tab. Both are US-first and drew a privacy backlash, which leaves room for a self-hosted, PSD2-based, bring-your-own-model tool for Italy and France. The self-hosted AI-finance projects that already exist have little traction, so success depends on execution more than on the idea.

The PRD should build a thin custom core: a Python cron, SQLite, deterministic recurring detection and a small UI. It should not try to compete with full budgeting apps. The cron runs with no LLM. Categorization follows a cascade: rules first, then a local model or Haiku only for the long tail. Claude Code on the Max plan does the analysis, on demand or as a low-frequency digest, and never in the ingestion path. **One operational trap matters before any code is written. Italian banks commonly allow only one active consent per provider per user, so consenting a bank from a new script can silently revoke the consent BankMCP already holds.**

## Sync, labels and dashboards exist; coaching and memory do not

The overlap is wide, but it ends early in the pipeline. **Actual Budget** has native Enable Banking sync, but it is marked experimental, starts manually and stores sync tokens on the server without end-to-end encryption ([Actual docs](https://actualbudget.org/docs/advanced/bank-sync/); [Actual: Enable Banking](https://actualbudget.org/docs/advanced/bank-sync/enable-banking)). The community bridge **enable-actual** adds scheduled imports and session-expiry alerts ([enable-actual](https://github.com/2manyvcos/enable-actual)). **Firefly III**'s Data Importer supports Enable Banking, GoCardless, SimpleFIN and CAMT.053 ([Firefly III docs](https://docs.firefly-iii.org/how-to/data-importer/import/third-party-providers/)). **actual-ai** (MIT, about 528 stars) categorizes transactions with Ollama, Anthropic, OpenAI and other providers. It runs on a cron, tags its guesses for review, suggests new categories and searches the web for unknown merchants ([actual-ai](https://github.com/sakowicz/actual-ai)). That is almost exactly the planned classification step, already built.

The most complete single overlap is **Sure**, the community fork of the abandoned Maybe Finance. It has about 10.4k stars and is AGPLv3. It has beta Enable Banking support, an AI assistant, LLM categorization and recurring-transaction detection ([GitHub we-promise/sure](https://github.com/we-promise/sure); [Sure discussion #388](https://github.com/we-promise/sure/discussions/388)). The cost is a Rails, Postgres and Redis stack, and EU sync is still beta. The closest match in spirit is **Syllogic**: self-hosted, Enable Banking connectivity, recurring-charge tracking and a native MCP server for Claude. It had about 5 GitHub stars when indexed ([gittrend](https://gittrend.io/repo/syllogic-ai/syllogic)). Other small projects include OpenCoffer (SimpleFIN only, BYO-LLM, MCP), Finvo and FinanzPilot ([Glama: OpenCoffer](https://glama.ai/mcp/servers/osirishorus/opencoffer); [Finvo](https://github.com/kylesean/finvo); [LinuxLinks: FinanzPilot](https://www.linuxlinks.com/finanzpilot-self-hosted-personal-finance-web-application/)). Your own **BankMCP** gives live, read-only access to European banks, but by design it stores no transactions and has no analysis layer ([Railway: BankMCP](https://railway.com/deploy/bankmcp)).

The subscription tools in the open-source world are mostly manual trackers: Wallos, SubTrackr and SubOS ([Wallos](https://github.com/ellite/Wallos); [SubTrackr](https://selfhostyourself.com/services/subtrackr)). Automatic detection exists only inside PFM add-ons such as Toolbox for Firefly III ([Firefly third-party apps](https://docs.firefly-iii.org/references/firefly-iii/third-parties/apps/)). Nothing open-source handles cancellation or renegotiation. The existing Claude skills either analyse a one-off CSV or PDF ([finance-manager](https://claudemarketplaces.com/skills/ailabs-393/ai-labs-claude-skills/finance-manager)) or focus on portfolio maths ([personal-finance-coach](https://claudemarketplaces.com/skills/erichowens/some_claude_skills/personal-finance-coach)). Neither works from a synced EU ledger with a liabilities memory.

**Is there interest?** At mass scale, yes. ChatGPT Personal Finance launched in May 2026 for US Pro users. It is read-only through Plaid and shows spending, subscriptions and upcoming payments ([MacRumors](https://www.macrumors.com/2026/05/15/chatgpt-personal-finance); [Plaid blog](https://plaid.com/blog/chatgpt-personal-finance-plaid/)). An unreleased "Claude Money" tab was spotted in September 2026 ([TestingCatalog](https://www.testingcatalog.com/anthropic-prepares-claude-money-for-personal-finance)). Community reaction featured distrust of handing bank access to an AI company, fear that the data would feed training, and worry about LLM arithmetic errors. Self-hosters pushed local-model alternatives ([Singularity Moments](https://singularitymoments.com/content/openai-wants-your-bank-login-and-the-internet-is-losing-its-mind/)). That source is anecdotal, but every complaint in it maps onto a design choice this project can make.

France already has polished aggregators: Linxo has more than 3 million users, and Finary is building an "AI agent" with €25m of new funding ([Le Journal des Entreprises](https://www.lejournaldesentreprises.com/article/fintech-linxo-leve-20-millions-deuros-110049); [FrenchWeb](https://www.frenchweb.fr/finary-leve-25-millions-deuros-pour-accelerer-sur-lia-appliquee-a-la-gestion-de-patrimoine/457143)). Italy has no Finary equivalent, so the gap there is wider. The honest reading: this is a **strong personal tool and a credible niche open-source project, not a proven mass market**. Very low star counts on comparable repos show that audience demand is unproven.

## Enable Banking makes ingestion free, but consent is the fragile part

Enable Banking's free "restricted mode" is the only realistic free and compliant PSD2 route for an individual in 2026. GoCardless stopped accepting new Bank Account Data accounts in July 2025 ([Actual: GoCardless](https://actualbudget.org/docs/advanced/bank-sync/gocardless/)). The Terms limit production use to linked accounts "solely for evaluation purposes or for the personal use of private individuals" and state that use is free of charge ([Enable Banking Terms](https://enablebanking.com/terms)). A cron reading your own accounts fits squarely within those Terms. Publishing the code as open source is fine. Hosting it for others or shipping one shared app key is not: each user must register their own application.

Authentication uses a locally signed RS256 JWT, then `POST /auth`, a browser SCA step and `POST /sessions`. Consent lasts until `valid_until`, which is capped by each bank's maximum and has **no refresh step** ([EB API reference](https://enablebanking.com/docs/api/reference/); [EB FAQ](https://enablebanking.com/docs/faq/)). A live catalogue pull through BankMCP on 2026-10-04 showed **337 of 339 Italian banks at 180 days**. Almost all French banks were at 180 days too; Trade Republic is at 90. The script therefore needs two modes: an interactive `consent` command run about twice a year, and an unattended daily `fetch`. It should alert about 14 days before expiry and on any invalid-session error. enable-actual already does this with ntfy ([enable-actual](https://github.com/2manyvcos/enable-actual)).

**Caution: do not re-consent a bank from the new script while BankMCP holds a consent for it.** Enable Banking's Italy docs warn that "many Italian banks enforce one active consent per TPP per user" and that starting a new consent invalidates the previous one ([EB Italy market docs](https://enablebanking.com/docs/markets/it/)). With Enable Banking, the licensed provider (the TPP) is Enable Banking itself, whichever application you register. Creating a second application may therefore not protect you, even though enable-actual recommends one application per bank for other reasons. That is an inference; no source settles it. The PRD should name **one consent owner per bank**. Either the cron becomes the only holder and analysis reads the local database instead of BankMCP, or the cron reuses BankMCP's existing session (BankMCP keeps its config in `/data/bank.json` ([Railway: BankMCP](https://railway.com/deploy/bankmcp))). Test any change on a low-stakes account first. The second reason to consolidate is the rate limit. Many banks allow **only 4 background fetches per day** and return HTTP 429 `ASPSP_RATE_LIMIT_EXCEEDED` beyond that ([EB FAQ](https://enablebanking.com/docs/faq/); [EB API reference](https://enablebanking.com/docs/api/reference/)). BankMCP calls on demand and cron calls draw on the same allowance.

The data needs care in three places. **History**: many banks give 1 to 3 years of history only shortly after first consent, then drop to 90 days. Pull with `strategy=longest` immediately after each consent, then fetch incrementally ([EB FAQ](https://enablebanking.com/docs/faq/)). **Deduplication**: key on `entry_reference`, not `transaction_id`. Some banks omit or duplicate references, and pending items usually have none ([EB FAQ](https://enablebanking.com/docs/faq/)). Use a fallback hash fingerprint, keep pending rows in a separate table that each run replaces, and store the raw JSON. **Coverage**: every major IT and FR bank is listed, but Intesa Sanpaolo, BNP Paribas and the Crédit Agricole regional banks are flagged beta. UniCredit and Mediolanum exclude credit-card accounts from PSD2 ([EB Italy market docs](https://enablebanking.com/docs/markets/it/)). A CSV, OFX, CAMT.053 or PDF import path is therefore a requirement, not a nice-to-have. Bank APIs also break: Crédit Agricole had a 13-day outage at another aggregator in October 2025 ([Powens status](https://powens.statuspal.eu/incidents/208291)).

## Rules first, small model second: LLM categorization costs cents a year

**"Jev" is not a taxonomy or an open model.** The only match the research found is TypeSafe's "Jev" decision model. Norman Finance uses it in production to choose one category from a pre-filtered list, with a median latency of 265 ms in a synthetic test ([Norman Finance blog](https://norman.finance/de/en/blog/fast-ai-categorization-jev)). The research found no evidence that it can be self-hosted and no price, so confirm that this is what you meant. The *pattern* behind Jev is more useful than the model itself:

1. Explicit rules.
2. Memory of the user's past corrections.
3. An LLM choosing from a list of eligible categories, filtered by payment direction and given up to five similar past choices.
4. A fallback for invalid or low-confidence answers.

Algoan describes the same cascade, with a structured output schema and a human review queue whose corrections feed the next iteration ([Algoan blog](https://www.algoan.com/en/blog/from-raw-data-to-model-update-an-automatic-categorization-pipeline)). Choosing the most similar labelled examples as few-shot demonstrations consistently beats random selection ([Loukas et al.](https://arxiv.org/pdf/2308.14634)).

The evidence argues for personalisation over model size. On 14,799 SME transactions, zero-shot labelling reached **80% accuracy** against expert annotation. Rare and ambiguous categories did badly, and cross-company generalisation fell to **48%** ([Jess et al., ICAIF'24](https://www.sea.dev/assets/ICAIF_workshop_paper-llms.pdf)). A generic model cannot know that "BONIFICO A ROSSI M." is your rent; your correction history can. For a local option, a June 2026 study found fine-tuned **Qwen 3.5-4B at 96.6% F1** for merchant extraction, 3.8 times faster than an 8B baseline. Qwen 3.5-0.8B reached 94.75% ([arXiv 2606.08051](https://arxiv.org/abs/2606.08051)). Those figures are for fine-tuned extraction, not zero-shot categorization of Italian or French bank strings, and no head-to-head benchmark on EU consumer data exists.

Cost should not drive the model choice. At Haiku 4.5 prices ($1 per million input tokens, $5 per million output; batch $0.50/$2.50) ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)), about 400 input and 30 output tokens per transaction comes to roughly **$0.55 per 1,000 transactions in real time and $0.28 in batch**. A household with 100 to 300 transactions a month, of which only 10 to 30% reach the LLM after rules, spends cents per year. **Choose between local and cloud on privacy and convenience, not price.**

Recommended PRD spec for categorization. Normalise descriptors deterministically first: strip "PAGAMENTO POS", "ADDEBITO SDD", "PRLV SEPA", "CB", dates and masked card numbers, and keep the SEPA creditor ID and creditor name as stable keys. Then run the stages in order:

1. Rules on the normalised merchant, IBAN or creditor ID.
2. The correction memory.
3. kNN over local multilingual embeddings, auto-accepting when the nearest neighbours agree.
4. A local Qwen or Gemma 4 to 8B model through Ollama, with grammar-constrained JSON over a closed category list and the amount sign as a hard filter. Haiku 4.5 is an optional fallback below a confidence threshold.
5. A review queue in the UI.

Ask the model to return the normalised merchant name as well as the category, so each new merchant reaches the LLM only once. Base the taxonomy on Plaid's two-level PFC, which has 16 primary and 104 detailed categories plus confidence levels ([Plaid](https://plaid.com/blog/transactions-categorization-taxonomy/)). Add EU leaves: utilities (luce, gas, acqua), condominio, bollo auto, RCA, mutuo, LOA, buoni pasto and F24 or impôts payments. **Build an eval set of 300 to 500 hand-labelled transactions from your own history before choosing a model.** Track accuracy per category and the share of transactions sent to review, and rerun it on every prompt or model change. No published benchmark substitutes for it.

## Claude Code runs on demand, never in the ingestion path

The question "when does the LLM run?" has a clean answer. **Ingestion never uses an LLM. Categorization uses the local or cheap model at ingest time. Claude Code runs analysis in two modes:** interactively, when you open the project and ask, and as a weekly or monthly `claude -p "/monthly-review"` from your own cron. Deterministic code raises alerts (price increase, missed payment, consent expiry). The LLM explains them only when asked or in the digest.

That split follows Anthropic's policy. Subscription OAuth is for "ordinary use of Claude Code". Developers building products "including those using the Agent SDK, should use API key authentication". Max credentials must not be routed on behalf of other users. Advertised limits "assume ordinary, individual usage" ([Claude Code legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). As of 15 June 2026, `claude -p` draws on normal subscription limits because the planned separate SDK credit pool was paused ([Claude support](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)). The policy has already changed twice in 2026. **Keep categorization off the subscription. Do not share the coach with family members through your Max login. Design every skill so that it also runs with an API key**; Sonnet 5.5 costs $2/$10 per million tokens ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)).

The analysis layer maps onto Claude Code primitives:

- **Skills** in `.claude/skills/`, one per job: `monthly-review`, `subscription-audit`, `contract-check`, `offer-comparison` and `loan-analysis`.
- **A subagent** for web research.
- **A read-only MCP server or SQL CLI** over the local database, which replaces BankMCP as the analysis data source.
- **Deterministic Python tools** for every number: amortization, annualised subscription cost, LOA-versus-buy, early-repayment savings.

The LLM interprets results and does not compute them. That answers the arithmetic criticism directly.

Memory needs two tiers. **Facts that drive calculations go in SQLite tables:**

- `liabilities`: lender, principal, fixed or variable rate, term, instalment, and a matcher linking it to its bank transaction.
- `amortization_schedule`: generated by code.
- `contracts`: provider, renewal date, notice period, legal regime and source PDF.
- `assets`: for example, LOA residual value and option price.
- `goals`.

**Narrative context goes in markdown files** that Claude Code loads: `memory/profile.md` for goals, plans and risk tolerance, and `memory/decisions.md` for past advice and its outcome. Linking each liability to its detected recurring payment lets reconciliation flag a variable-rate change or a missed instalment without involving an LLM.

The subscription workflow should be deterministic up to the point of judgement. Detection groups payments by normalised merchant or SEPA creditor ID and requires at least 3 occurrences. Every gap must fall inside a cadence window (weekly 7±2 days, monthly 30±5, annual 365±15), and amounts must stay within ±15% ([offbook PR #413](https://github.com/gregwym/offbook/pull/413)). Add a **bimonthly bucket**, because Italian utilities often bill every two months, and a wider amount tolerance for consumption-based bills. A recurring SDD or PRLV SEPA debit with the same creditor ID is close to ground truth.

Contract review should extract a fixed JSON schema from the PDF, quoting clauses verbatim with page numbers. A versioned, cited rules file should then decide cancellability, rather than the model's memory. Examples of rules:

- **Bersani (Italy, L. 40/2007):** telecom contracts can be withdrawn at any time with at most 30 days' notice, and charges not justified by costs are null ([AGCOM/Co.Re.Com](https://www.agcom.it/sites/default/files/migration/deliberazione/Deliberazione%20Co.re.com.%2018-03-2016%201479380292989.pdf)).
- **Loi Hamon (France):** auto and home insurance can be terminated without penalty after one year.
- **Loi Chatel (France):** providers of tacitly renewed contracts must notify the renewal deadline ([AG2R explainer](https://www.ag2rlamondiale.fr/particulier/auto-habitation/conseil-loi-chatel-et-loi-hamon-comment-resilier-une-assurance)).

Later reforms were not verified, so every rule needs a "last checked" date.

The "cheaper alternatives" search is feasible and cheap ($10 per 1,000 searches on the API ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing))) but unreliable. Comparator prices are dynamic, depend on consumption and postcode, sit behind forms, and are often promotional. Prefer the official comparators: ARERA's Portale Offerte in Italy and the energie-info comparator in France. Their current URLs and terms were not verified. Require a URL, a retrieval date and an annual cost based on your actual consumption for every quote. Never switch providers automatically, and never bypass a CAPTCHA.

## Privacy and regulation set the limits

For self-use, the legal exposure is low. GDPR's household exemption covers a person analysing their own finances, but it is read narrowly and lost once there is a commercial link. The cloud provider stays subject to GDPR, and transactions contain third-party names and can reveal health or religious data ([Irish DPC](https://dataprotection.ie/en/faqs/general/what-household-exemption); [Recital 18](https://presencis.com/regulations/gdpr/recital-18/)). Anthropic's commercial and API terms exclude training and default to 30-day retention. Consumer Pro and Max accounts that opted into training can be retained for up to 5 years ([Anthropic data usage](https://docs.claude.com/en/docs/claude-code/data-usage); [Implicator.ai](https://www.implicator.ai/anthropics-five-year-data-plan-for-claude-consumer-users/)). **Check your Max account's training setting.** Add a redaction layer that replaces IBANs, personal names and references with stable pseudonyms before any cloud call, and log what was sent to which model.

The regulatory line is investment advice, not budgeting. Personalised recommendations on specific financial instruments need authorisation: CIF status with ORIAS and the AMF in France (Finary itself is a registered CIF), and Consob authorisation in Italy, where unauthorised advice can carry criminal consequences ([CMS Francis Lefebvre](https://cms.law/fr/fra/a-la-une/newsletter-financial-services-n-1-eclairage-sur-le-service-d-investissement); [Finary legal](https://finary.com/fr/legal); [Consob](https://www.consob.it/web/area-pubblica/-/comunicazione-consob-del-2024-11-18-)). Advising yourself is not a regulated service. Published prompts should still avoid naming specific ETFs or funds and should carry Italian and French disclaimers. A budgeting coach is not high-risk under the AI Act. Credit scoring of natural persons is, and those obligations were delayed to December 2027 ([William Fry](https://www.williamfry.com/knowledge/high-risk-ai-in-financial-services/); [Leaseurope](https://www.leaseurope.org/new-application-dates-high-risk-ai-system-rules)). PSD3 and the PSR will not apply before about 2028 ([Arthur Cox](https://www.arthurcox.com/insights/psd3-and-psr-final-compromise-texts-published/)).

For security: encrypt the database at rest with SQLCipher or an encrypted volume ([SQLCipher overview](https://bitcoinlib.readthedocs.io/en/0.7.9/source/_static/manuals.sqlcipher.html)). Keep the Enable Banking PEM key in the OS keychain with mode 600; protecting it is a contractual duty ([Enable Banking Terms](https://enablebanking.com/terms)). Bind the UI to localhost or Tailscale. **Treat transaction descriptions as untrusted input.** A payer controls the remittance text, so a Claude Code session with web and file tools that reads it is exposed to prompt injection. Give analysis skills read-only database access and no write tools by default.

## PRD-ready decisions, scope and roadmap

**Build or extend.** Build a thin core and borrow designs. The differentiators (liabilities linked to transactions, contracts, a free label taxonomy) need first-class tables that Actual's envelope model and Sure's heavy stack would fight. The commodity parts are small: a Python cron using `PyJWT` and `httpx` (Enable Banking publishes Python samples ([enablebanking GitHub](https://github.com/enablebanking))), plus SQLite. Copy consent handling and alerts from enable-actual, the categorizer's review and "guessed" design from actual-ai, and detection rules from offbook. The credible alternative is to extend Actual with actual-ai and an Actual MCP server. That is faster to a polished UI, but you inherit manual or experimental sync and an envelope taxonomy. Pick it only if building the UI is the part you most want to avoid.

| Layer | Recommendation | LLM? |
|---|---|---|
| Ingestion | Python cron, 1–2 runs a day, single consent owner per bank, `strategy=longest` after consent, 10-day lookback, pending table replaced each run, raw JSON kept, ntfy alert 14 days before expiry | None |
| Import fallback | CSV / OFX / CAMT.053 / PDF for credit cards and outages | None (PDF parse optional) |
| Store | SQLite + SQLCipher: transactions, pending, merchants, rules, corrections, recurring, liabilities, contracts, assets, goals | — |
| Categorization | Normalise → rules → correction memory → kNN → local 4–8B model (Ollama, JSON grammar) → optional Haiku 4.5 → review queue | Local or cheap model, long tail only |
| Recurring and alerts | Deterministic cadence detection (including bimonthly), price-increase, missed-payment and new-subscription alerts | None |
| UI | Server-rendered (e.g. FastAPI with HTMX or similar): review queue, monthly view, recurring list, calendar, memory forms | None |
| Analysis | Claude Code skills + read-only MCP/SQL + Python calc tools; interactive, plus weekly or monthly `claude -p` digest; API-key fallback | Claude (Max or API) |
| Privacy | Pseudonymisation before cloud calls, send log, localhost/Tailscale, keys in keychain | — |

| Phase | Scope | Exit criterion |
|---|---|---|
| MVP (weeks 1–4) | Consent + daily fetch for one IT bank, dedup, CSV import, rules + local-model categorization, review queue, eval set, recurring detection, Claude Code `monthly-review` and `subscription-audit` | ≥90% accuracy on own eval set after corrections; 30 days of unattended sync |
| Phase 2 | Liabilities and contracts memory, amortization tools, `contract-check` with rules file, upcoming-payments calendar (iCal), price-increase and missed-payment alerts, cash-flow forecast | Every recurring debit linked to a subscription, contract or liability |
| Phase 3 | `offer-comparison` via official comparators, mortgage renegotiation/surroga check, tax-deduction tagging, net worth, goals | Each suggestion cites a source and an annual saving computed by code |
| Phase 4 (optional) | FR banks, multi-household members with their own SCA, open-source release (BYO Enable Banking app) | Clean install by a third party in under an hour |

Extra features worth adding, beyond those already planned. The **cash-flow forecast** and **upcoming-payment calendar** come almost free once recurring payments and liabilities exist: project the balance 30 to 90 days ahead and flag a likely overdraft. Linxo's overdraft alerts show that users value this ([Finary vs Linxo](https://finary.com/fr/budget/linxo-vs-finary-comparatif)). **Price-increase and anomaly alerts** (a subscription up more than 5%, a duplicate charge, a first-time merchant above a threshold) are deterministic and high value. A **mortgage renegotiation or surroga check** compares the stored loan with a rate you enter and computes the savings and break-even in code. No current market-rate source was researched. **Tax-deduction tracking** tags candidate deductible expenses (medical, mortgage interest, school and similar) for the Italian 730 or the French income-tax return. It should flag candidates and keep receipts linked, not calculate the deduction, because the rules were not verified here and change every year. **Net worth** combines bank balances with the liabilities and assets memory. **Goals** tie surplus cash flow to a target date. Other features:

- **Consent and connector health** on a status page.
- **A household mode** in which each account holder completes their own SCA.
- **A "decision journal"** that records each recommendation and whether it was acted on, so the coach can follow up.

Low-traction peers suggest skipping chatbot polish and mobile apps until the core loop proves useful to you.

| Risk | Likelihood | Mitigation |
|---|---|---|
| New consent revokes BankMCP's (Italian one-consent rule) | High if ignored | Single consent owner per bank; retire or repoint BankMCP; test on one low-stakes bank |
| Beta connectors, missing credit cards, outages | High | File-import fallback; health alerts; raw JSON retained |
| Unstable IDs and pending-to-booked duplicates | Medium | `entry_reference` + fingerprint fallback; separate pending table |
| Subscription policy for `claude -p` changes again | Medium | Low-frequency use only; skills portable to an API key |
| LLM arithmetic or legal hallucination | Medium | Code computes; versioned cited rules file; verbatim clause quotes |
| Prompt injection via remittance text | Low–medium | Read-only tools; treat descriptions as data; no autonomous actions |
| Stale or personalised comparator prices | High | Official comparators, URL and date per quote, re-verify before switching |
| Drifting into investment advice when published | Low for self-use | No named instruments; IT/FR disclaimers |

## Conclusion

The research changes the project's centre of gravity. The four steps the brief opens with (sync, classify, store, display) are now commodity, and a weekend of reuse covers them. The work worth doing is turning a ledger into decisions: linking every recurring debit to a contract or liability, knowing which ones can legally be cancelled and when, and pricing alternatives against your real consumption. Big-tech products will take a long time to do this for Italian contracts, PSD2 consents and mutuo amortization, and existing open-source projects have not tried.

The architecture follows from one principle: **the LLM never computes, never ingests and never acts; it reads code-produced facts and explains them.** That keeps cost near zero, makes the system portable between a Max subscription, an API key and a local model, and answers the main criticisms of commercial AI-finance products (trust, training on user data, arithmetic errors). The real unknowns are operational rather than conceptual: how each of your banks behaves with consents, entry references and credit cards. The first milestone should therefore be 30 days of clean, unattended sync from a single consent owner, before any coaching skill is written.
